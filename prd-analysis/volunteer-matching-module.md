## 1. 功能清單

### F9: 多維匹配引擎

| 屬性 | 詳情 |
|------|------|
| **優先級** | P0 (MVP必須) |
| **核心用戶故事** | 作爲求助者，系統能在30秒內爲我匹配到合適的志願者 |
| **技術方案** | Supabase Edge Functions (Deno) 實現匹配算法，PostgreSQL + PostGIS 存儲志願者位置信息 |
| **驗收標準** | 1. 匹配耗時 ≤ 30秒 (首次推送) <br> 2. 30秒無人接單自動擴大搜索範圍 <br> 3. 60秒仍無響應提示轉爲異步留言 |

**關鍵實現細節:**
- 匹配權重算法: `匹配分 = 0.30×緊急度 + 0.25×地理距離 + 0.20×技能匹配度 + 0.15×信譽分 + 0.10×歷史配對親密度`
- 技能標籤: 醫療輔助、外語翻譯(英/日/韓/法)、技術指導、心理支持、出行導航、生活常識、手語
- 流程: AI處理失敗 → 提取求助類型/緊急度/位置 → 查詢在線志願者池 → 計算Top 5 → 並行推送 → 首個接單建立連接

## 2. 匹配算法詳細設計

### 2.1 匹配權重算法

```
匹配分 = w1×緊急度 + w2×地理距離 + w3×技能匹配度 + w4×信譽分 + w5×歷史配對親密度

權重係數:
├── w1 (緊急度)       = 0.30  — 緊急需求優先
├── w2 (地理距離)     = 0.25 — 優先附近志願者
├── w3 (技能匹配)     = 0.20 — 需求與志願者技能標籤匹配
├── w4 (信譽分)       = 0.15 — 高信譽優先
└── w5 (歷史親密度)   = 0.10 — "老搭檔"加分
```

**各維度計算方式:**

| 維度 | 計算方式 | 說明 |
|------|----------|------|
| 緊急度 | 映射值: normal=0.4, important=0.6, urgent=0.8, emergency=1.0 | 來自F1意圖識別結果 |
| 地理距離 | `1 - min(距離/5km, 1)` | 5km內線性衰減，超出爲0 |
| 技能匹配度 | 匹配標籤數 / 需求標籤數 | 完全匹配=1.0，無匹配=0 |
| 信譽分 | 志願者credit_score / 5.0 | 滿分5分，歸一化到0-1 |
| 歷史親密度 | min(配對次數/10, 1) × 0.5 + 平均評分/5 × 0.5 | 最多計算10次歷史配對 |

### 2.2 匹配流程狀態機

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   pending   │────▶│  matching   │────▶│  connected  │
│   (待匹配)   │     │  (匹配中)    │     │  (已連接)    │
└─────────────┘     └──────┬──────┘     └─────────────┘
       ▲                   │
       │                   ▼
       │            ┌─────────────┐
       │            │   timeout   │────▶ 轉爲異步留言
       │            │  (超時無響應) │
       │            └─────────────┘
       │
       └────────────────────────────────
```

**狀態說明:**

| 狀態 | 觸發條件 | 超時處理 |
|------|----------|----------|
| pending | AI判斷無法獨立處理，進入匹配 | - |
| matching | 已向Top 5志願者推送 | 30秒擴大範圍，60秒轉異步 |
| connected | 有志願者接單，建立連接 | - |
| cancelled | 用戶取消或系統超時 | - |

### 2.3 超時處理機制

```
T+0s   ──▶ 開始向Top 5志願者並行推送
       ──▶ 推送內容: 求助類型、距離、預估耗時

T+30s  ──▶ 無人接單?
       ──▶ YES: 擴大搜索範圍至Top 10，降低匹配閾值
       ──▶ NO: 建立連接

T+60s  ──▶ 仍無響應?
       ──▶ YES: 提示用戶"當前志願者繁忙，是否轉爲異步留言?"
       ──▶ NO: 建立連接

T+5min ──▶ 異步任務仍未被領取?
       ──▶ 重新分配至更廣志願者池
```

### 3.3 屏幕共享實現

**技術方案:**
- **Android**: MediaProjection API 捕獲屏幕 → 創建 VideoTrack → 通過 WebRTC 發送
- **iOS**: ReplayKit 框架捕獲屏幕 → 自定義視頻源 → WebRTC 傳輸

**實現要點:**

| 功能 | 實現方式 | 注意事項 |
|------|----------|----------|
| 屏幕捕獲 | 系統級API (MediaProjection/ReplayKit) | 需要用戶授權 |
| 視頻編碼 | VP8 或 H.264 | 考慮弱網自適應碼率 |
| 遠程標註 | 數據通道傳輸座標 + 本地繪製 | 標註同步延遲 < 100ms |
| 權限控制 | 僅志願者可發起標註請求 | 求助者可隨時關閉標註 |

**屏幕共享流程:**
```
1. 求助者開啓屏幕共享
   └── 請求 MediaProjection 授權
   └── 創建 ScreenCaptureIntent
   └── 啓動前臺服務 (避免被系統殺死)

2. 視頻流建立
   └── 創建 VideoSource (類型: SCREEN)
   └── 添加到 PeerConnection
   └── 通過 SDP offer/answer 協商

3. 志願者端接收
   └── 渲染到 SurfaceViewRenderer
   └── 支持手勢標註 (觸摸座標通過DataChannel回傳)

4. 求助者端顯示標註
   └── 接收 DataChannel 座標數據
   └── 在屏幕疊加層繪製標註
```

## 4. SOS緊急流程

### 4.1 觸發條件

| 觸發方式 | 觸發條件 | 防誤觸機制 |
|----------|----------|------------|
| 語音觸發 | F8檢測到緊急關鍵詞 | 5秒倒計時確認，無響應自動觸發 |
| 按鍵觸發 | 連按電源鍵3次 | 3秒內完成，間隔 < 1秒 |
| 長按觸發 | 首頁大按鈕長按3秒 | 震動反饋 + 語音播報確認 |
| 手動觸發 | SOS頁面點擊確認 | 立即觸發 |

### 4.2 廣播機制

```
┌─────────────────────────────────────────────────────────────────┐
│                        SOS觸發                                  │
└───────────────────────────┬─────────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  1. 獲取精確位置 (GPS + 基站 + WiFi)                            │
│     └── 精度目標: 室內 < 50m，室外 < 10m                        │
└───────────────────────────┬─────────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  2. 並行廣播推送                                                │
│     ├── 推送A: 5km內所有在線志願者 (最高優先級，繞過勿擾模式)    │
│     ├── 推送B: 緊急聯繫人短信 (含位置鏈接)                       │
│     └── 推送C: (可選) 自動撥打120/110 (需用戶預授權)            │
└───────────────────────────┬─────────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  3. 響應處理                                                    │
│     ├── 首個接單志願者建立連接                                  │
│     └── 其他志願者收到"已被響應"通知                            │
└───────────────────────────┬─────────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. 升級策略 (無響應時)                                         │
│     ├── T+5min: 擴大至全城志願者                               │
│     ├── T+10min: 強制通知所有緊急聯繫人 (電話+短信)              │
│     └── T+15min: 記錄爲"高風險事件"，運營人工介入               │
└─────────────────────────────────────────────────────────────────┘
```

### 4.3 升級策略

| 時間節點 | 升級動作 | 目標 |
|----------|----------|------|
| T+0 | 5km半徑廣播 | 最近志願者 |
| T+5min | 擴大至全城 | 所有在線志願者 |
| T+10min | 強制通知緊急聯繫人 | 求助者親友 |
| T+15min | 運營人工介入 | 平臺兜底 |

**SOS專用數據表字段:**
```sql
sos_requests (
  id UUID PK,
  seeker_id UUID FK,
  location GEOGRAPHY(POINT),
  location_accuracy FLOAT, -- 精度(米)
  trigger_method TEXT, -- 'voice'/'button'/'long_press'
  status TEXT, -- 'active'/'responded'/'escalated'/'resolved'
  responder_id UUID FK, -- 響應志願者
  emergency_contacts_notified BOOLEAN[],
  escalation_level INT DEFAULT 0,
  created_at TIMESTAMPTZ,
  resolved_at TIMESTAMPTZ
)
```

## 5. MVP vs V1.0 範圍

### 5.1 MVP必須實現 (P0)

| 功能 | 實現程度 | 關鍵驗收點 |
|------|----------|------------|
| **F9 多維匹配引擎** | 簡化版 | 基礎權重算法(緊急度+距離)，30秒響應 |
| **F11 實時語音通話** | 完整版 | WebRTC語音，5秒內建立，錄音存儲 |
| **F13 SOS緊急廣播** | 完整版 | 3種觸發方式，5km廣播，聯繫人通知 |

**MVP簡化點:**
- 匹配算法: 暫不考慮技能匹配和歷史親密度
- 語音通話: 僅實現基礎功能，暫不支持弱網自適應
- SOS: 暫不支持自動撥打120/110

### 5.2 V1.0延後實現 (P1/P2)

| 功能 | 優先級 | 延後原因 | V1.0實現要求 |
|------|--------|----------|--------------|
| **F10 異步留言** | P1 | 非核心流程，MVP可用實時通話替代 | 完整異步隊列，24小時SLA |
| **F12 視頻+屏幕共享** | P1 | 技術複雜度高，WebRTC視頻需更多調試 | 視頻通話+屏幕標註+AI輔助 |
| **F16 常用志願者** | P1 | 依賴歷史數據積累 | 親密度權重算法，重逢提示 |
| **F18 完整等級體系** | P1 | 運營屬性強，MVP可簡化 | 7級成長體系，積分商城 |
| **F22 異步任務隊列** | P1 | 配合F10實現 | 任務篩選，領取機制 |

### 5.3 技術債務清單

**MVP階段可接受的技術債務:**

1. **匹配算法簡化**
   - 債務: 僅使用緊急度+距離兩個維度
   - 風險: 匹配精準度降低
   - 償還計劃: V1.0引入技能標籤和歷史親密度

2. **WebRTC信令**
   - 債務: 使用Supabase Realtime作爲信令通道
   - 風險: 高併發時可能不穩定
   - 償還計劃: V1.0評估是否需要自建信令服務器

3. **SOS升級策略**
   - 債務: 僅實現5km廣播，暫不支持全城
   - 風險: 偏遠地區可能無人響應
   - 償還計劃: V1.0實現動態範圍擴展
