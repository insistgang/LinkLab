## 1. 功能清单

### F9: 多维匹配引擎

| 属性 | 详情 |
|------|------|
| **优先级** | P0 (MVP必须) |
| **核心用户故事** | 作为求助者，系统能在30秒内为我匹配到合适的志愿者 |
| **技术方案** | Supabase Edge Functions (Deno) 实现匹配算法，PostgreSQL + PostGIS 存储志愿者位置信息 |
| **验收标准** | 1. 匹配耗时 ≤ 30秒 (首次推送) <br> 2. 30秒无人接单自动扩大搜索范围 <br> 3. 60秒仍无响应提示转为异步留言 |

**关键实现细节:**
- 匹配权重算法: `匹配分 = 0.30×紧急度 + 0.25×地理距离 + 0.20×技能匹配度 + 0.15×信誉分 + 0.10×历史配对亲密度`
- 技能标签: 医疗辅助、外语翻译(英/日/韩/法)、技术指导、心理支持、出行导航、生活常识、手语
- 流程: AI处理失败 → 提取求助类型/紧急度/位置 → 查询在线志愿者池 → 计算Top 5 → 并行推送 → 首个接单建立连接

## 2. 匹配算法详细设计

### 2.1 匹配权重算法

```
匹配分 = w1×紧急度 + w2×地理距离 + w3×技能匹配度 + w4×信誉分 + w5×历史配对亲密度

权重系数:
├── w1 (紧急度)       = 0.30  — 紧急需求优先
├── w2 (地理距离)     = 0.25 — 优先附近志愿者
├── w3 (技能匹配)     = 0.20 — 需求与志愿者技能标签匹配
├── w4 (信誉分)       = 0.15 — 高信誉优先
└── w5 (历史亲密度)   = 0.10 — "老搭档"加分
```

**各维度计算方式:**

| 维度 | 计算方式 | 说明 |
|------|----------|------|
| 紧急度 | 映射值: normal=0.4, important=0.6, urgent=0.8, emergency=1.0 | 来自F1意图识别结果 |
| 地理距离 | `1 - min(距离/5km, 1)` | 5km内线性衰减，超出为0 |
| 技能匹配度 | 匹配标签数 / 需求标签数 | 完全匹配=1.0，无匹配=0 |
| 信誉分 | 志愿者credit_score / 5.0 | 满分5分，归一化到0-1 |
| 历史亲密度 | min(配对次数/10, 1) × 0.5 + 平均评分/5 × 0.5 | 最多计算10次历史配对 |

### 2.2 匹配流程状态机

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   pending   │────▶│  matching   │────▶│  connected  │
│   (待匹配)   │     │  (匹配中)    │     │  (已连接)    │
└─────────────┘     └──────┬──────┘     └─────────────┘
       ▲                   │
       │                   ▼
       │            ┌─────────────┐
       │            │   timeout   │────▶ 转为异步留言
       │            │  (超时无响应) │
       │            └─────────────┘
       │
       └────────────────────────────────
```

**状态说明:**

| 状态 | 触发条件 | 超时处理 |
|------|----------|----------|
| pending | AI判断无法独立处理，进入匹配 | - |
| matching | 已向Top 5志愿者推送 | 30秒扩大范围，60秒转异步 |
| connected | 有志愿者接单，建立连接 | - |
| cancelled | 用户取消或系统超时 | - |

### 2.3 超时处理机制

```
T+0s   ──▶ 开始向Top 5志愿者并行推送
       ──▶ 推送内容: 求助类型、距离、预估耗时

T+30s  ──▶ 无人接单?
       ──▶ YES: 扩大搜索范围至Top 10，降低匹配阈值
       ──▶ NO: 建立连接

T+60s  ──▶ 仍无响应?
       ──▶ YES: 提示用户"当前志愿者繁忙，是否转为异步留言?"
       ──▶ NO: 建立连接

T+5min ──▶ 异步任务仍未被领取?
       ──▶ 重新分配至更广志愿者池
```

### 3.3 屏幕共享实现

**技术方案:**
- **Android**: MediaProjection API 捕获屏幕 → 创建 VideoTrack → 通过 WebRTC 发送
- **iOS**: ReplayKit 框架捕获屏幕 → 自定义视频源 → WebRTC 传输

**实现要点:**

| 功能 | 实现方式 | 注意事项 |
|------|----------|----------|
| 屏幕捕获 | 系统级API (MediaProjection/ReplayKit) | 需要用户授权 |
| 视频编码 | VP8 或 H.264 | 考虑弱网自适应码率 |
| 远程标注 | 数据通道传输坐标 + 本地绘制 | 标注同步延迟 < 100ms |
| 权限控制 | 仅志愿者可发起标注请求 | 求助者可随时关闭标注 |

**屏幕共享流程:**
```
1. 求助者开启屏幕共享
   └── 请求 MediaProjection 授权
   └── 创建 ScreenCaptureIntent
   └── 启动前台服务 (避免被系统杀死)

2. 视频流建立
   └── 创建 VideoSource (类型: SCREEN)
   └── 添加到 PeerConnection
   └── 通过 SDP offer/answer 协商

3. 志愿者端接收
   └── 渲染到 SurfaceViewRenderer
   └── 支持手势标注 (触摸坐标通过DataChannel回传)

4. 求助者端显示标注
   └── 接收 DataChannel 坐标数据
   └── 在屏幕叠加层绘制标注
```

## 4. SOS紧急流程

### 4.1 触发条件

| 触发方式 | 触发条件 | 防误触机制 |
|----------|----------|------------|
| 语音触发 | F8检测到紧急关键词 | 5秒倒计时确认，无响应自动触发 |
| 按键触发 | 连按电源键3次 | 3秒内完成，间隔 < 1秒 |
| 长按触发 | 首页大按钮长按3秒 | 震动反馈 + 语音播报确认 |
| 手动触发 | SOS页面点击确认 | 立即触发 |

### 4.2 广播机制

```
┌─────────────────────────────────────────────────────────────────┐
│                        SOS触发                                  │
└───────────────────────────┬─────────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  1. 获取精确位置 (GPS + 基站 + WiFi)                            │
│     └── 精度目标: 室内 < 50m，室外 < 10m                        │
└───────────────────────────┬─────────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  2. 并行广播推送                                                │
│     ├── 推送A: 5km内所有在线志愿者 (最高优先级，绕过勿扰模式)    │
│     ├── 推送B: 紧急联系人短信 (含位置链接)                       │
│     └── 推送C: (可选) 自动拨打120/110 (需用户预授权)            │
└───────────────────────────┬─────────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  3. 响应处理                                                    │
│     ├── 首个接单志愿者建立连接                                  │
│     └── 其他志愿者收到"已被响应"通知                            │
└───────────────────────────┬─────────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│  4. 升级策略 (无响应时)                                         │
│     ├── T+5min: 扩大至全城志愿者                               │
│     ├── T+10min: 强制通知所有紧急联系人 (电话+短信)              │
│     └── T+15min: 记录为"高风险事件"，运营人工介入               │
└─────────────────────────────────────────────────────────────────┘
```

### 4.3 升级策略

| 时间节点 | 升级动作 | 目标 |
|----------|----------|------|
| T+0 | 5km半径广播 | 最近志愿者 |
| T+5min | 扩大至全城 | 所有在线志愿者 |
| T+10min | 强制通知紧急联系人 | 求助者亲友 |
| T+15min | 运营人工介入 | 平台兜底 |

**SOS专用数据表字段:**
```sql

  responder_id UUID FK, -- 响应志愿者

  escalation_level INT DEFAULT 0,
  created_at TIMESTAMPTZ,
  resolved_at TIMESTAMPTZ
)
```

## 5. MVP vs V1.0 范围

### 5.1 MVP必须实现 (P0)

| 功能 | 实现程度 | 关键验收点 |
|------|----------|------------|
| **F9 多维匹配引擎** | 简化版 | 基础权重算法(紧急度+距离)，30秒响应 |
| **F11 实时语音通话** | 完整版 | WebRTC语音，5秒内建立，录音存储 |
| **F13 SOS紧急广播** | 完整版 | 3种触发方式，5km广播，联系人通知 |

**MVP简化点:**
- 匹配算法: 暂不考虑技能匹配和历史亲密度
- 语音通话: 仅实现基础功能，暂不支持弱网自适应
- SOS: 暂不支持自动拨打120/110

### 5.2 V1.0延后实现 (P1/P2)

| 功能 | 优先级 | 延后原因 | V1.0实现要求 |
|------|--------|----------|--------------|
| **F10 异步留言** | P1 | 非核心流程，MVP可用实时通话替代 | 完整异步队列，24小时SLA |
| **F12 视频+屏幕共享** | P1 | 技术复杂度高，WebRTC视频需更多调试 | 视频通话+屏幕标注+AI辅助 |
| **F16 常用志愿者** | P1 | 依赖历史数据积累 | 亲密度权重算法，重逢提示 |
| **F18 完整等级体系** | P1 | 运营属性强，MVP可简化 | 7级成长体系，积分商城 |
| **F22 异步任务队列** | P1 | 配合F10实现 | 任务筛选，领取机制 |

### 5.3 技术债务清单

**MVP阶段可接受的技术债务:**

1. **匹配算法简化**
   - 债务: 仅使用紧急度+距离两个维度
   - 风险: 匹配精准度降低
   - 偿还计划: V1.0引入技能标签和历史亲密度

2. **WebRTC信令**
   - 债务: 使用Supabase Realtime作为信令通道
   - 风险: 高并发时可能不稳定
   - 偿还计划: V1.0评估是否需要自建信令服务器

3. **SOS升级策略**
   - 债务: 仅实现5km广播，暂不支持全城
   - 风险: 偏远地区可能无人响应
   - 偿还计划: V1.0实现动态范围扩展
