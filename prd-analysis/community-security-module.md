## 1. 社羣功能清單

### 1.1 F24: 興趣小組（SIG）

| 屬性 | 詳情 |
|------|------|
| **優先級** | P2 |
| **功能定位** | 按專業技能/興趣劃分的垂直社羣 |
| **預設小組** | 醫療輔助組、外語翻譯組、心理支持組等 |
| **用戶價值** | 志願者可加入感興趣的領域，與同好交流經驗 |
| **技術實現** | 需羣聊/論壇功能、成員管理、內容審覈 |

**關鍵設計要點：**
- 與F19技能標籤聯動，志願者加入對應SIG可獲得該領域更多匹配機會
- 可作爲F27新手村的實踐基地，老志願者在SIG中指導新人

**關鍵設計要點：**
- 與F9匹配引擎的地理距離權重形成互補

## 2. 安全體系設計

### 2.1 F28: 多級認證體系詳細流程

#### 認證層級表

| 用戶類型 | 認證等級 | 認證方式 | 獲得權益 |
|----------|----------|----------|----------|
| 求助者（殘障） | 基礎認證 | 手機號 + 實名 | 基礎求助功能 |
| 求助者（殘障） | 優先認證 | + 殘疾證/盲協證明 | 優先匹配權、專屬標識 |
| 求助者（普通） | 標準認證 | 手機號 + 實名 | 基礎求助功能 |
| 志願者 | 基礎認證 | 手機號 + 實名 + 信用分（芝麻/微信） | 基礎幫助功能 |
| 志願者 | 認證技能 | + 專業證明上傳 + 人工審覈 | 技能標籤展示、高權重匹配 |

#### 認證流程圖

```text
註冊 → 手機號驗證 → 身份選擇（求助者/志願者）
    ↓
求助者路徑：
    ├── 基礎信息填寫（障礙類型、偏好設置）
    ├── 可選：上傳殘障證明 → 人工審覈（48h）→ 獲得優先標識
    └── 完成

志願者路徑：
    ├── 基礎信息填寫
    ├── 第三方信用授權（芝麻/微信信用分）
    ├── 選擇技能標籤
    ├── 需認證技能？→ 上傳證明文件 → 人工審覈
    └── 完成
```

#### 技術實現要點

1. **證件審覈**：OCR識別證件信息 + 人工複覈
2. **信用接入**：支付寶芝麻信用/微信信用分API對接
3. **審覈時效**：承諾48小時內完成審覈
4. **狀態管理**：認證狀態實時同步到用戶資料

### 2.2 F29: 錄音與內容檢測方案

#### 錄音方案

| 項目 | 設計 |
|------|------|
| **默認狀態** | 默認開啓 |
| **用戶控制** | 可在F17偏好設置中關閉 |
| **存儲時長** | 7天自動刪除 |
| **存儲位置** | 國內合規雲存儲 |
| **加密要求** | 端到端加密存儲 |
| **訪問權限** | 僅用於糾紛處理，需審批調取 |

#### AI內容檢測方案

| 檢測類型 | 觸發條件 | 處理方式 |
|----------|----------|----------|
| 辱罵/人身攻擊 | 實時語音轉文本分析 | 自動警告 + 記錄標記 |
| 敏感內容 | 涉黃/涉暴/涉政關鍵詞 | 自動中斷 + 人工複覈 |
| 詐騙誘導 | 金錢交易、個人信息索取 | 實時提醒用戶 + 標記上報 |
| 異常行爲 | 長時間沉默、重複呼叫 | 系統提示 + 自動掛斷 |

#### 技術架構

```text
通話流 → WebRTC → 實時轉寫（訊飛ASR）→ NLP分析
    ↓
檢測到違規 → 實時警告（雙方）→ 記錄標記
    ↓
通話結束 → 錄音文件 → 加密存儲 → 7天后自動刪除
```

### 2.3 F30: 雙向互評與信用分算法

#### 評價流程

```text
通話結束 → 彈出評價頁 → 雙方互評
    ↓
求助者評價志願者：1-5星 + 可選文字感謝
志願者評價求助者：1-5星 + 可選標籤（禮貌/惡意/騷擾）
    ↓
評價結果 → 信用分計算 → 影響後續匹配權重
```

#### 信用分算法設計

**基礎分制**：5分制，新用戶默認5.0分

**分數變動規則**：

| 行爲 | 分數變動 | 說明 |
|------|----------|------|
| 獲得5星評價 | +0.1 | 單次上限 |
| 獲得4星評價 | +0.05 | 單次上限 |
| 獲得3星及以下 | -0.2 | 單次上限 |
| 被有效舉報 | -1.0 | 視嚴重程度 |
| 連續10次好評 | +0.3 | 額外獎勵 |
| 30天無違規 | +0.1 | 月度獎勵 |

**匹配權重影響**：

```
匹配分 = ... + w4×信譽分 + ...

信譽分權重規則：
- 4.5-5.0分：正常權重
- 4.0-4.5分：權重×0.8
- 3.5-4.0分：權重×0.5，限制匹配頻率
- <3.5分：暫停匹配，需人工審覈
```

### 2.4 F31: 舉報處理流程

#### 舉報入口

- **位置**：通話結束頁、歷史記錄頁、通話中快捷按鈕
- **方式**：一鍵舉報，選擇舉報原因，可選上傳證據

#### 舉報處理流程

```text
用戶舉報 → 系統記錄 → 臨時凍結雙方匹配（24h）
    ↓
人工審覈隊列 → 48h內完成審覈
    ↓
    ├── 舉報成立 → 處理被舉報人 + 通知舉報人
    │       ├── 輕微違規：警告 + 信用分扣減
    │       ├── 嚴重違規：封號7-30天
    │       └── 惡意違規：永久封號 + 設備指紋封禁
    │
    └── 舉報不成立 → 恢復匹配 + 記錄標記
```

#### 黑名單機制

| 黑名單類型 | 觸發條件 | 影響範圍 |
|------------|----------|----------|
| 用戶級 | 被多次舉報覈實 | 該賬號永久封禁 |
| 設備級 | 同一設備多次違規 | 設備指紋封禁，該設備無法註冊 |
| IP級 | 同一IP批量註冊違規賬號 | IP段限制註冊 |

### 2.5 F32: 緊急聯繫人管理

#### 功能設計

| 項目 | 設計 |
|------|------|
| **設置數量** | 最多3個緊急聯繫人 |
| **信息字段** | 姓名、電話、關係、優先級（1-3） |
| **觸發條件** | F13 SOS廣播自動觸發 |
| **通知方式** | 短信 + Push通知 |
| **通知內容** | 包含位置鏈接的求助信息 |

#### 觸發流程

```text
SOS觸發 → 獲取精確位置（GPS+基站）
    ↓
並行通知：
    ├── 推送半徑5km內所有志願者
    ├── 發送短信給緊急聯繫人（含位置鏈接）
    └── 可選：自動撥打120/110（需用戶授權）
```

## 3. 隱私保護方案

### 3.1 數據存儲與加密

| 數據類型 | 存儲方案 | 加密方式 | 保留期限 |
|----------|----------|----------|----------|
| 用戶身份信息 | PostgreSQL | 字段級AES加密 | 賬號存續期 |
| 通話錄音 | 對象存儲 | 端到端加密 | 7天自動刪除 |
| 位置信息 | PostgreSQL（PostGIS） | 座標偏移處理 | 求助結束後模糊化 |
| 聊天記錄 | PostgreSQL | 字段級加密 | 賬號存續期 |
| 評價記錄 | PostgreSQL | 字段級加密 | 賬號存續期 |

### 3.2 位置信息處理

#### 精度分級

| 精度級別 | 使用場景 | 誤差範圍 |
|----------|----------|----------|
| 精確位置 | SOS緊急求助 | <10米 |
| 模糊位置 | 普通匹配 | 100-500米 |
| 城市級 | 社羣歸屬展示 | 僅顯示城市名 |

#### 位置模糊化算法

```python
# 僞代碼示例
def fuzzy_location(lat, lng, level):
    if level == 'precise':
        return (lat, lng)
    elif level == 'fuzzy':
        # 添加隨機偏移
        offset_lat = random.uniform(-0.005, 0.005)
        offset_lng = random.uniform(-0.005, 0.005)
        return (lat + offset_lat, lng + offset_lng)
    elif level == 'city':
        # 返回城市中心座標
        return get_city_center(lat, lng)
```

### 3.3 身份信息隔離

#### 隔離原則

| 場景 | 可見信息 | 隔離措施 |
|------|----------|----------|
| 匹配階段 | 求助類型、距離、預估耗時 | 雙方真實身份互不可見 |
| 通話過程中 | 系統生成的臨時暱稱 | 真實姓名、電話隱藏 |
| 通話結束後 | 可選顯示感謝信（脫敏） | 聯繫方式仍不可見 |
| 常用志願者 | 暱稱 + 歷史合作次數 | 需雙方同意才顯示更多信息 |

#### 技術實現

- 使用系統生成的UUID作爲通話標識
- WebRTC通話使用臨時Token，過期失效
- 真實身份信息僅存儲於服務端，前端不可直接訪問

## 4. 風險應對

### 4.1 PRD風險清單與應對措施

| 風險 | 影響 | 涉及的安全功能 | 具體應對措施 |
|------|------|----------------|--------------|
| **冷啓動期志願者不足** | 求助無人響應 | F13 SOS廣播、F9匹配引擎 | 1. 種子用戶計劃（10-20名核心志願者）<br>2. 運營團隊模擬求助兜底<br>3. 高校合作招募<br>4. SOS擴大廣播半徑（5km→全城） |
| **AI誤判緊急度** | 延誤緊急求助或誤觸SOS | F8緊急檢測、F13 SOS廣播 | 1. 二次確認機制（5秒倒計時+語音確認）<br>2. 緊急詞庫持續優化<br>3. 用戶反饋閉環訓練<br>4. 手動觸發SOS作爲備選（連按電源鍵3次） |
| **隱私泄露** | 法律風險+用戶流失 | F28認證、F29錄音、F32緊急聯繫人 | 1. 端到端加密存儲<br>2. 數據最小化原則<br>3. 7天自動刪除錄音<br>4. 定期合規審計<br>5. 用戶數據導出與註銷權 |
| **API成本高** | 運營不可持續 | F1智能對話、AI Agent模塊 | 1. 分級調用策略（簡單任務用輕量模型）<br>2. 緩存常見查詢結果<br>3. 離線OCR作爲備選<br>4. 異步任務錯峯處理 |
| **惡意用戶騷擾** | 志願者流失+平臺聲譽 | F28認證、F30信用分、F31舉報 | 1. 多級認證提高註冊門檻<br>2. 信用分動態調節匹配權重<br>3. AI行爲檢測異常模式<br>4. 設備指紋封禁違規賬號<br>5. 雙向評價機制互相監督 |

### 4.2 額外風險識別

| 風險 | 應對策略 |
|------|----------|
| 志願者 burnout | F23排班功能限制推送時段、F22異步任務減輕實時壓力 |

| 位置信息被追蹤 | 模糊化處理、求助結束後位置數據脫敏 |

## 6. 關鍵設計建議

### 6.1 安全優先原則

1. **默認安全**：錄音默認開啓、位置默認模糊、認證默認嚴格
2. **最小權限**：志願者與求助者之間信息隔離，僅展示必要信息
3. **快速響應**：舉報48小時內處理、SOS 5分鐘無響應自動升級

### 6.2 社羣漸進策略

1. **MVP冷啓動**：不依賴社羣功能，專注1對1互助體驗
2. **V1.0培育**：先建立核心志願者SIG，再擴展地區社羣
3. **內容運營**：精選故事作爲情感紐帶，新手村保證服務質量
