## 1. 项目摘要

共感 LinkAble 是一个面向无障碍社会互助场景的 AI+X 应用。项目将人工智能引入视障、听障、老年人及临时困难人群的即时求助流程，构建“AI 第一响应、真人志愿者兜底、SOS 安全闭环”的协同服务系统。系统以 AI Agent 为统一入口，接收文字、语音、拍照和位置等多模态输入，识别用户意图与风险等级，优先处理 OCR 朗读、药品说明、场景描述、颜色识别、翻译转述等标准化问题；当 AI 低置信、问题复杂或涉及高风险时，系统自动转入志愿者匹配或 SOS 流程，避免用户停留在不确定的机器回答中。

与传统无障碍工具相比，本项目不是单点功能集合，而是将 AI 推理、风险分流、服务调度、无障碍交互和真人协作组织为端到端闭环。当前 MVP 已实现 AI 对话、志愿者匹配、Demo 语音通话、SOS Mock、登录偏好和全局无障碍适配，支持无真实 API key、无真实 WebRTC、无真实推送条件下稳定演示，便于初赛视频和现场答辩复现。

## 2. 问题背景与应用价值

无障碍服务存在三个典型断点：

1. 标准化问题响应慢：例如读药品说明、看路牌、识别环境、理解通知单等任务频繁出现，但用户不一定能快速获得帮助。
2. 复杂问题缺少真人兜底：AI 可以处理部分信息任务，但涉及线下行动、医疗风险、导航判断或突发事件时，单纯给出文本建议并不安全。
3. 求助流程认知负担高：现有工具往往将 OCR、语音、拍照、志愿者、紧急联系人拆散，用户需要先判断该用哪个功能，这对视障、老年或紧急状态下用户并不友好。

据世界卫生组织公开信息，全球约有 13 亿人经历显著残障，约占全球人口 16%。在中国，残障人口规模也长期处于千万级以上。无障碍技术不是小众优化，而是数字公共服务的重要组成部分。本项目选择“AI+无障碍民生服务”作为应用场景，目标是降低即时求助门槛，提高标准化问题响应效率，并在高风险场景保留人类协助与安全闭环。

## 3. 技术调研与已有工作对比

现有相关方案可以分为三类：

| 类型 | 代表能力 | 优势 | 局限 |
|---|---|---|---|
| 单点辅助工具 | OCR、读屏、颜色识别、语音助手 | 功能明确，响应快 | 功能割裂，无法完成风险分流和服务调度 |
| 通用大模型聊天 | 问答、翻译、图像描述 | 泛化能力强，交互自然 | 缺少求助状态机，不保证低置信转人工，不适合紧急场景独立闭环 |
| 公益互助平台 | 志愿者报名、帮助信息发布 | 有真人服务资源 | 首次响应慢，需求描述不标准，匹配与安全控制不足 |

LinkAble 的差异化在于：把 AI 从“回答者”升级为“第一响应智能体”。系统不追求让 AI 替代志愿者，而是让 AI 先完成需求结构化、紧急程度判断和可标准化任务处理；一旦 AI 不确定或存在现实行动需求，立即将任务交给真人志愿者或 SOS 流程。该模式兼顾 AI 效率与人类协作的可靠性。

## 4. 作品创新性

### 4.1 AI Agent 第一响应机制

系统将用户输入统一归入 Agent facade，标准化为 `input_type`、`intent`、`urgency`、`confidence`、`next_action` 等结构化字段。AI 输出不直接裸露给用户，而是经过意图识别、风险判断和 UI 文案归一化后再展示。

核心动作包括：

- AI 可处理：直接回答并提供朗读、继续追问、转人工兜底。
- AI 低置信：追问澄清或进入志愿者匹配。
- 高风险：进入 SOS，不走普通匹配。
- 用户主动要求真人：直接进入匹配。

### 4.2 “AI+真人”协同调度

项目避免把志愿者当作静态资源池，而是将志愿者匹配作为 AI 分流后的行动层。匹配依据包括任务类型、技能标签、距离、可用状态、历史信任和信誉分。当前 MVP 以可复现 Demo 池实现匹配逻辑，后续真实模式可接入地理位置、在线状态与数据库原子接单。

### 4.3 面向无障碍的安全状态机

项目定义了从 `created`、`ai_processing`、`ai_resolved`、`matching`、`connected` 到 `completed/expired/cancelled` 的求助状态机。每个状态都有可见 UI、读屏文案和降级路径，避免“AI 失败后没有去路”。

### 4.4 Demo-first 与真实集成隔离

竞赛版本默认走本地 DemoMode。无 API key、弱网或真实 SDK 失败时，仍可完成 3 分钟闭环演示。这体现工程落地的鲁棒性，也避免把外部服务稳定性风险转嫁到比赛展示。

## 5. 系统架构

```text
用户输入层
文字 / 语音 / 拍照 / 位置
        |
        v
AI Agent 第一响应层
意图识别 / 紧急度判断 / 置信度评估 / 安全文案生成
        |
        +--> AI 直接解决：OCR、药品说明、场景描述、颜色识别、翻译转述
        |
        +--> 志愿者匹配：低置信、复杂需求、用户主动转人工
        |
        +--> SOS：紧急意图、求救关键词、高风险场景
        |
        v
协助闭环层
Demo Call / 状态回看 / 评价 / 安全记录 / 无障碍偏好
```

工程实现采用 Flutter + Riverpod，核心能力通过 facade 隔离：

| Facade | 职责 |
|---|---|
| `AgentServiceFacade` | 统一 AI/OCR/ASR/Vision 入口，输出标准 AgentResponse |
| `VolunteerMatchingFacade` | 志愿者匹配与候选排序 |
| `CallSessionFacade` | Demo Call 与未来真实 WebRTC 适配 |
| `SosFacade` | SOS 撤销、广播、联系人通知状态 |
| `AccessibilityPrefsFacade` | 字体、对比度、朗读、触觉等偏好 |

## 6. AI 推理流程与指标设计

### 6.1 输入输出模型

输入统一为：

```json
{
  "input_type": "text | voice | image | location | mixed",
  "text": "用户文字或语音转写",
  "image_uri": "可选图片",
  "location": "可选位置",
  "accessibility_prefs": {
    "screen_reader": true,
    "large_text": true,
    "high_contrast": true,
    "voice_output": true
  },
  "network_status": "online | weak | offline",
  "demo_mode": true
}
```

输出统一为：

```json
{
  "intent": "medicine_check",
  "urgency": "normal | elevated | emergency",
  "confidence": 0.91,
  "can_resolve_by_ai": true,
  "answer_text": "可读屏文本",
  "next_action": "answer | ask_followup | match_volunteer | trigger_sos",
  "recommended_volunteer_tags": ["视障协助", "医院导诊"],
  "safety_flags": [],
  "ui_copy": {
    "title": "AI 已识别需求",
    "primary_action": "继续识别",
    "secondary_action": "转人工确认"
  }
}
```

### 6.2 指标体系

| 指标 | 含义 | 初赛建议目标 | 当前验证方式 |
|---|---|---:|---|
| 意图识别准确率 | 识别 9 类主意图是否正确 | >= 85% | 构造 90 条用例，每类 10 条 |
| 紧急意图召回率 | 对“救命、迷路、摔倒”等紧急输入是否触发 SOS | >= 95% | 紧急样本集 + 非紧急对照 |
| 紧急误报率 | 普通问题误触发 SOS 的比例 | <= 2% | 普通样本回归测试 |
| 决策正确率 | `answer / ask_followup / match_volunteer / trigger_sos` 是否合理 | >= 85% | 人工标注 gold action |
| 首次响应时间 | 用户提交到首个可见状态 | <= 3s | Flutter 日志 + stopwatch |
| 匹配计算耗时 | 50 人志愿者池 Top 5 排序耗时 | <= 500ms | 本地匹配基准测试 |
| 无障碍适配 | 200% 字体、48dp 触控、读屏语义 | 主要页面通过 | Widget test + 真机抽检 |

当前代码已具备本地 Demo 数据与闭环测试基础，后续提交前需将上述测试结果汇总为表格和截图，放入“其他辅助材料”压缩包。

## 7. 数据、行业知识、算法与硬件来源

### 7.1 数据来源

- Demo 数据：项目本地构造的无敏感信息样例，包括药品说明、场景描述、紧急词、志愿者标签和帮助场景。
- 评测数据：建议由团队自建匿名文本样本集，不采集真实用户隐私；每条样本仅保留文本、期望意图、期望动作。
- 行业知识：无障碍交互规范、WCAG 对比度与文本缩放要求、药品场景安全边界、紧急求助流程设计。

### 7.2 算法来源

- 意图识别：关键词规则 + 本地确定性 Demo response + 可扩展 LLM prompt 分类。
- 风险判断：紧急词检测、低置信阈值、医疗/导航/现实行动风险规则。
- 志愿者匹配：基于可用性、距离、技能匹配、历史信任、信誉分的加权排序。
- 通话与 SOS：状态机驱动，真实 WebRTC、推送、短信目前为后续扩展。

### 7.3 硬件来源

当前 MVP 依赖普通 Android 手机即可运行。输入能力包括触屏、麦克风、摄像头和系统朗读；竞赛 Demo 不依赖专用硬件。

## 8. 工程实现与初期成果

当前 Flutter 原型已完成以下闭环：

1. 首页：预置会话进入，无需现场注册。
2. AI 助手：支持简单药品问答、OCR/场景描述、紧急词检测和转人工。
3. 志愿者匹配：AI 无法处理或用户主动要求时进入匹配页。
4. Demo Call：模拟语音通话连接、已接通、通话中和结束状态。
5. SOS：展示误触撤销、模拟广播和联系人通知。
6. 我的/偏好：展示字体、显示模式、朗读和安全设置。
7. 无障碍：主要控件具备语义标签，支持大触摸目标和 200% 字体测试。

## 9. 安全、隐私与伦理

本项目面向潜在弱势用户，因此必须保持安全边界：

- AI 不替代医疗、法律等专业判断。
- 药品相关问题只做说明辅助和风险提示，不给个性化诊断。
- 低置信、高风险、现实行动需求必须转人工或 SOS。
- Demo 不保存真实姓名、手机号、精确位置和图片原文。
- 真实版本中精确位置仅在求助、匹配、SOS 时启用。
- 日志只记录匿名 ID、request ID、feature name。

## 10. 应用落地与社会价值

LinkAble 的应用价值不只在于提供一个 AI 问答入口，而在于构建“AI+社会互助”的服务组织方式：

- 对用户：减少求助步骤，降低认知负担，提升日常任务独立性。
- 对志愿者：先由 AI 完成标准化筛查，减少无效沟通，提高接单效率。
- 对机构：可作为社区、医院、校园、交通枢纽等公共服务场景的无障碍补充入口。
- 对 AI+X 研究：提供了从模型推理到服务调度、从技术演示到社会落地的可验证路径。
